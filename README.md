# 钉钉文档文件夹打包下载（Chrome 扩展）

钉钉文档网页端只能一个文件一个文件地点下载。这个扩展在**你自己的浏览器里**读取
文件夹的完整目录树，让你勾选后批量下载，并保留原有的子文件夹结构，或者打包成一个 zip。

登录态用的是你自己浏览器的钉钉会话，扩展不会读取、上传或存储你的账号凭据。

## 安装

1. 打开 `chrome://extensions/`
2. 右上角打开「开发者模式」
3. 点「加载已解压的扩展程序」，选择本目录（`dd-batch-dl`）
4. 建议把它固定到工具栏

## 使用

1. 在浏览器里打开你的钉钉文档文件夹页面（确认已登录、能正常看到文件列表）
2. 点扩展图标 → 打开侧边栏（会一直留在标签页上，用侧边栏自带的 ✕ 关闭）
3. 当前页面地址**会自动填入**，直接点「扫描目录树」
4. **点文件夹左边的小三角展开它** —— 展开哪个才去读哪个，不会一次性遍历整个目录
5. 勾选要下载的内容（支持搜索过滤、全选、反选）
6. 点「下载选中的文件」

文件会保存到 Chrome 的下载目录，并保持文件夹结构。

**下载路径相对于你勾选的东西**，扫描时用的入口目录不会成为多余的一层：

| 你勾选的 | 下载到的位置 |
|---|---|
| 子文件夹「产品A」（里面有 `手册/说明书.pdf`） | `产品A/手册/说明书.pdf` |
| 根目录下的散文件 `顶层文件.txt` | `顶层文件.txt` |
| 整个根目录 | `顶层文件.txt`、`产品A/手册/说明书.pdf` |

（根目录名只出现在 zip 的**文件名**上，不会作为压缩包内的顶层文件夹。）

> 链接输入框在打开侧边栏时就会自动填好，一般**不需要手动操作**。
> 「重新读取当前页面」只是切换标签页后重新读一次；也可以直接粘贴链接。

### 关于侧边栏会一直留在标签页上

这是 Chrome 侧边栏本身的**行为特征**，不是 bug：

- **没有**任何 API 能让扩展关闭自己的侧边栏；
- 用 `setOptions({ enabled: false })` 在别的标签页上禁用，**不会**把用户已经打开的面板收掉；
- 唯一能做的是 `setPanelBehavior({ openPanelOnActionClick: true })`（点图标开关面板）
  和用户自己点 ✕ 关闭。

曾经尝试过用「注入页面的浮层」替代侧边栏来绕开这一点，但**在真实钉钉文档页面上无法做到可靠**，
已回退。所以这里保留侧边栏，并把上面的限制写清楚，避免以后有人重复踩坑。

### 下载目录

面板里的「下载到」是一个**相对浏览器下载目录的子文件夹**——`chrome.downloads` 只接受
相对路径，无法指定绝对路径。留空就下到默认目录。

点「位置…」会打开 Chrome 的下载设置，可以改**默认下载目录本身**；改完之后，
上面填的子文件夹会建在那个新目录下。

### 关于文件夹大小

**精确大小和"不完整遍历"确实冲突，这是数据源决定的，不是实现偷懒。**

实测确认（见下）：钉钉**没有**任何能返回文件夹聚合大小的接口，而且**它自己的网页端也不显示文件夹大小**。
文件夹对象里只有一个 `dentryStatistic.childrenCount`（条目数）。所以一个文件夹的大小
只能由它下面所有文件的大小累加得出——那部分没读过，大小就无从得知。

因此扩展的做法是**不隐瞒**：

| 状态 | 显示 |
|---|---|
| 子树已完整读取 | 实际大小，如 `2.3 GB` |
| 子树未完整读取 | `大小未知`（灰色斜体），悬停提示说明原因 |

点「展开全部（算出大小）」即可算出精确大小。这一步的实测成本：

| 操作 | 请求数 | 并发 | 实测耗时 |
|---|---|---|---|
| 展开全部（288 个文件夹） | 288 次 | 6 | **~14 秒** |

（原先串行实现是 ~80 秒。单次请求的往返约 280ms 是主要成本，所以改并发收益很大。）

算出后**每个**文件夹都会显示自己的子树总大小，不只是根目录。校验方式是把根目录各子项
大小相加，与全树文件字节总和比对：`3575784779 == 3575784779` ✅。

### 关于 blob 下载地址（为什么有个离屏文档）

MV3 的 Service Worker **没有 DOM，因此 `URL.createObjectURL` 不存在**。这是实测确认的：

```
在真实 Service Worker 里：
  typeof URL.createObjectURL      → "undefined"
  调用它                          → TypeError: URL.createObjectURL is not a function
  typeof chrome.offscreen         → "object"
  chrome.downloads 接受 blob:     → ✅
  chrome.downloads 接受 data:     → ✅（但几 MB 以上会被 Chrome 拒绝）
```

所以 zip 打包完成后，Blob 会被交给一个**离屏文档**（`src/offscreen.html`），
由它（有 DOM）创建 `blob:` 地址并把地址交回来，Service Worker 再拿这个地址去下载。
离屏文档只在需要生成 zip 时创建。若离屏方式失败，会退回 `data:` URL（仅适用于小文件），
两条都失败时会把两次的错误原因一并报出来。

**数据必须分块传输**：`chrome.runtime.sendMessage` 有 **64 MiB 硬上限**
（实测：32 MB 通过、64 MB 抛 `Message exceeded maximum allowed size of 64MiB`），
而 base64 还会再膨胀 1/3——单条消息根本装不下一个真实压缩包，硬发的结果是
**一个损坏的空 zip**。所以每 4 MiB 一块发送，离屏文档按块重组，
并且重组后会**核对字节数**，不一致就直接报错而不是给你一个坏文件。

实测（真实 Service Worker 内）：

| 载荷 | 结果 |
|---|---|
| 8 MB / 64 MB / 100 MB | 逐字节一致（`firstDiff: -1`） |
| 单条消息 64 MB（对照） | 抛 64MiB 超限错误 |

### 懒加载

扫描只读取**根目录一层**，子文件夹的内容在你展开它时才去请求：

| 操作 | 请求数 | 实测耗时 |
|---|---|---|
| 扫描根目录 | 3 次 | 0.6 秒 |
| 展开一个文件夹 | 1 次 | ~0.3 秒 |
| 再次展开（已缓存） | 0 次 | 立即 |
| 展开全部（288 个文件夹，并发 6） | 288 次 | ~14 秒 |

所以打开一个几百个文件夹的文档空间是**瞬间**的，不再需要等一分多钟。

**勾选整个文件夹不需要先展开它** —— 下载时后台会按 uuid 逐个解析里面的文件。
小三角变成 `…` 表示正在读取；文件夹右侧的 `·` 表示尚未展开（不是"空文件夹"）。

勾选一个未展开的文件夹后，扩展会**自动在后台把它解析出来**（只解析你勾选的那些，
不会顺手遍历整棵树），这样文件数和大小才能显示，下载按钮也才会亮。

### 三个选项

| 选项 | 效果 |
|---|---|
| 扁平化 | 忽略目录结构，所有文件下到同一个文件夹，重名自动加序号 |
| 打包成一个 zip | 把选中内容压成一个 zip 文件再下载。文件会先读进内存，**大文件夹请改用逐个下载**（扩展会在超过约 1.8 GB 时拦住你） |
| 展开全部（算出大小） | 递归读取所有子文件夹，并发 6，288 个文件夹约 14 秒。之后每个文件夹的精确大小、统计数字和 zip 体积预估才是完整的 |

## 实测验证情况

本扩展是用真实账号、真实文件夹端到端验证过的，不是只跑了静态检查。验证对象是一个
含 **503 个文件 / 288 个文件夹 / 3.4 GB** 的钉钉文档文件夹：

| 验证项 | 结果 |

| 扫描根目录（懒加载） | ✅ **0.6 秒 / 3 次请求**（改动前是 110 秒 / 292 次请求） |
| 展开单个文件夹 | ✅ 0.3 秒 / 1 次请求，且只取一层、不递归 |
| 重复展开 | ✅ 0 次请求（走缓存） |
| 展开全部 | ✅ 288 个文件夹全部加载（并发 6，~14 秒），统计与懒加载前完全一致 |

## 已知限制

- **钉钉在线文档**（文档 `.adoc`、表格 `.axls`、思维导图 `.amind` 等）在列表里会标成「在线」。
  这类文件没有公开的导出接口，扩展会跳过它们，并在末尾列出待手动处理的清单（带直达链接）。
  上传的文件（PDF / Word / Excel / 图片 / 压缩包等）正常批量下载。
- 需要你有该文件夹的**下载**权限，否则接口会拒绝。
- 下载地址是钉钉实时签发的，所以下载过程中请保持登录、不要关闭该文档页面。
- 首次扫描大文件夹（几百个以上文件）需要一点时间，扫描结果会缓存到 `chrome.storage.local`
  （上限 10 MB）。正常文件夹的目录树只有约 0.14 MB（实测 503 文件 / 288 文件夹），
  缓存失败也不会影响本次下载，只是重开侧边栏需要重新扫描。
- 页面代发（通道二）需要那个钉钉文档标签页保持打开。关掉页面后回退不可用。

## 工作原理

扩展有两条取数通道，正常情况下走第一条，被拒时自动切到第二条。

### 通道一：Service Worker 直接请求

Service Worker 用 `chrome.cookies` 读你自己会话里的 cookie，调用钉钉文档自身的接口：

| 用途 | 接口 | 关键参数 |
|---|---|---|
| 节点信息 | `GET /box/api/v2/dentry/info` | `dentryUuid`, `spaceId` |
| 列子项 | `GET /box/api/v2/dentry/list` | `dentryUuid`, `pageSize`（上限 50）, `loadMoreId`（游标） |
| 取文件下载地址 | `GET /box/api/v2/file/download` | `dentryUuid`, `spaceId` |

展开一个文件夹 = 一次 `/dentry/list`；下载一个文件 = 一次 `/file/download` 换签名地址。

### 通道二：页面代发（回退）

有些钉钉版本会把文档会话放在**`chrome.cookies` 读不到**的地方（partitioned storage，
或者 set 在了无法枚举的 host 上）。这种情况下通道一必然 401。

因为**页面自己永远有它自己的会话**，扩展在收到 401/403 时会把同一个请求
用 `chrome.scripting.executeScript` 注入到你已经打开的那个文档页面里发出去，
从而完整继承页面自己的凭据。一旦回退成功，后续请求直接走页面，不再重试通道一。

文件字节仍然由 Service Worker 直接取：签名后的 CDN 地址自带鉴权且不受 CORS 限制。
只有以下情况会触发回退：HTTP 401/403。其他状态码（如 400 参数错误）是服务端的真实回答，不会回退。

### 逆向出来的接口细节

都是实测确认的，不是猜的：

- **分页**：`size` / `page` / `offset` / `cursor` 这些参数服务端**全部忽略**。
  真正的契约是 `pageSize`（服务端硬上限 50）+ `loadMoreId`（上一页响应里的游标）。
  响应字段是 `data.children` / `data.hasMore` / `data.loadMoreId`。
- **下载地址**在 `data.cdnUrlPreSignatureInfo.cdnPreSignUrls[0]`，
  `data.downloadType = "CDN_URL_PRE_SIGNATURE"`。是 OSS 预签名地址，
  **不需要 Cookie** 即可取（已实测），但有时效（约 15 分钟）。
- **文件大小**字段是 `fileSize`，不是 `size`。
- **在线文档**靠 `contentType === "ALIDOC"` 识别最准；上传的文件是 `contentType: "document"`，
  且带 `extension` 字段（不带点，如 `pptx`）。
- 文件名里可能夹带零宽字符（钉钉的反爬手段），展示时会尽量清理。
- `spaceId` 不在 URL 里，需要从页面 HTML 里提取。
- **文件夹大小没有任何接口可查**。试过的、全部 404：`dentry/statistic`、`dentry/size`、
  `dentry/stat`、`dentry/children`、`dentry/tree`、`dentry/batchget`（GET/POST）、
  `dentry/statistic/batchget`、`space/statistic`、`dentry/quota`；
  `dentry/list` 加 `recursive` / `deep` / `withStatistic` / `scope=ALL` 也都被忽略。
  `dentry/info` 的响应里没有任何 size/bytes/total 字段。
  所以文件夹大小只能由扩展自己遍历累加。

## 排错

| 现象 | 原因 / 处理 |
|---|---|
| 红点、提示「没找到钉钉登录态」 | 先点右上角的**「诊断」**，它会列出每个 cookie 查询来源返回了什么、以及接口是否接受当前会话。若确认已登录还报这个，把诊断结果发我 |
| 提示「未能识别 spaceId」 | 确认目标页面已完全加载（地址栏是完整的钉钉文档链接），再重试 |
| 提示「链接里没找到 `/i/nodes/<id>`」 | 你填的不是节点链接。用「重新读取当前页面」而不是手动粘贴分享短链 |
| 侧边栏在所有标签页都显示 | Chrome 侧边栏的固有行为，扩展**无法**关闭它（见上文）。用侧边栏自带的 ✕ 关闭 |
| 输入框是空的 | 只有在钉钉文档页面上才会自动填入；切换标签页后点「重新读取当前页面」，或手动粘贴链接 |
| 部分文件失败 | 看侧边栏底部的「需要手动处理的项」清单，里面有具体原因和直达链接 |
| 明明有文件却显示「在线」被跳过 | 那些是钉钉在线文档，没有导出接口，只能在钉钉里手动导出 |
| 点小三角没反应 / 收不起来 | 已在 0.1.0 修复（CSS 里 `.node { display: block }` 覆盖了 `[hidden]`）。请刷新扩展 |
| 只勾选文件夹，下载按钮是灰的 | 勾选后扩展会自动解析该文件夹，稍等一下。若仍灰着，点「诊断」看是否有读取失败 |
| 点了「展开全部」还是显示「大小未知」 | 已在 0.1.0 修复（侧边栏没有合并后台算出的大小）。请刷新扩展 |
| 打包时提示 `URL.createObjectURL is not a function` | 已在 0.1.0 修复（Service Worker 里没有这个 API，改用离屏文档）。请刷新扩展 |
| 下载到的 zip 是空的 / 打不开 | 已在 0.1.0 修复（`runtime.sendMessage` 有 64 MiB 上限，单条消息装不下真实压缩包，导致文件被截断）。现在改为分块传输并核对字节数。请刷新扩展 |
| 想全部重新来 | `chrome://extensions/` 里点扩展的刷新按钮，然后重新扫描 |

### 诊断按钮

侧边栏右上角的「诊断」会输出：

- 当前页面 URL、识别到的会话 cookie、读到的 cookie 总数与去重后的名称列表（**不含 cookie 值**）
- 每个查询来源（带完整路径的页面 URL、`url:<origin>/`、`domain:dingtalk.com` 等）各返回多少项
- **关键对比**：①②两种发起方式的结果并排显示

| ① 扩展自身 | ② 实际方式 | 结论 |
|---|---|---|
| 200 | 200（经扩展自身） | 会话正常，直接扫描 |
| 401 | 200（经页面代发） | 扩展 cookie 不够，但回退已自动生效，直接扫描 |
| 401 | 非 200，且「未找到标签页」 | 请先在浏览器里打开该文件夹页面（回退需要它） |
| 401 | 非 200 | 当前账号对该节点没有访问权，或该链接不属于当前登录的文档空间 |

### 关于会话 cookie

不同版本的钉钉把文档会话放在不同的地方（旧版是 `doc_atoken`，较新的版本是 `dk` / `dk.sig` 一对，
而且这对 cookie **`chrome.cookies` 读不到**）。因此扩展：

1. **不靠 cookie 名字判断登录态**——只有服务端明确拒绝才算失败；
2. 被拒时自动改用页面代发（见上）。

另外注意 `chrome.cookies.getAll({url})` 是**路径敏感**的，会话 token 常被限制在某个子路径下，
所以扩展会把**当前页面的完整 URL** 也作为查询来源。

## 目录结构

```
manifest.json        扩展清单（MV3）
src/shared.js        公共工具：文件名清洗、去重、大小格式化、在线文档识别
src/background.js    Service Worker：钉钉接口调用、目录树扫描、下载/打包
src/zip.js           zip 组装器（CompressionStream + Blob 分段，避免整包进内存）
src/offscreen.js     Service Worker 里没有 URL.createObjectURL，由它负责生成 blob 地址
src/offscreen.html
src/sidepanel.html   侧边栏界面
src/sidepanel.css    样式（含深色模式）
src/sidepanel.js     界面逻辑：目录树渲染、勾选、进度、下载目录
```
